# CLAUDE.md — NeuroQuest

**Project:** NeuroQuest — 生理心理學冒險筆記  
**Version:** 1.0  
**Language:** 繁體中文（zh-TW）  
**Project Type:** Static Educational Website  
**Target:** GitHub Pages  
**Development Priority:** 學習內容正確性 > 測驗功能穩定性 > 使用體驗 > 視覺特效

---

## 1. Project Overview

NeuroQuest 是一個結合生理心理學課程筆記與像素 RPG 遊戲化測驗的教育網站。

使用者可以閱讀章節筆記，再透過回答問題攻擊怪獸。完成 10 題測驗後，依照正確題數獲得不同的星級獎勵。

本專案的主要目的包括：

1. 幫助使用者理解與複習生理心理學。
2. 透過遊戲化測驗增加學習趣味。
3. 建立可重複使用的章節、筆記與測驗架構。
4. 讓 AI 未來可以依照本文件持續擴充網站，而不必重新設計整個專案。

本文件是專案的長期開發規範。執行任務時，必須同時參考現有程式架構及本文件。

## 2. MVP Scope

目前優先完成 V1.0，開發範圍為：

- 一個可正常瀏覽的首頁。
- 一個完整開放的學習章節。
- 其他章節的 Coming Soon 入口。
- 一份具有完整結構的章節筆記。
- 一套 10 題測驗系統。
- 一隻具有簡單動畫的怪獸。
- 怪獸血量、計分、星級判定。
- 錯題回顧與重新挑戰。
- 每章最佳星級保存。
- GitHub Pages 部署。

V1.0 不包含：

- 使用者登入與帳號系統。
- 後端、資料庫或雲端同步。
- 多人排行榜。
- 可自由移動的 RPG 角色。
- 複雜戰鬥技能與遊戲引擎。
- 動態 AI 出題 API。
- 背景音樂或大型動畫素材。

除非使用者明確要求，不得擅自加入上述功能。

## 3. Technology Requirements

使用：

- HTML5
- CSS3
- Vanilla JavaScript
- JSON 或 JavaScript 資料模組
- Browser localStorage

技術限制：

1. 不使用後端。
2. 不使用付費 API。
3. 不要求使用者註冊帳號。
4. 優先避免需要額外安裝或編譯的框架。
5. 所有網站資源使用相對路徑。
6. 網站必須可部署到 GitHub Pages 的專案子路徑。
7. 優先使用本機資源，避免依賴不穩定的外部服務。
8. 不得將 API 金鑰、私人資料或未獲授權的教材放入公開 Repository。

開發時可以使用簡單的本機 HTTP Server 預覽。

不得依賴直接開啟 file:// 網址作為唯一測試方式。

## 5. Visual Design

### Overall Style

採用可愛、復古、像素 RPG（Pixel RPG）風格。

網站應保留教育網站的清晰度，不應為了遊戲外觀犧牲閱讀體驗。

### Design Principles

- 首頁呈現冒險地圖或 RPG 關卡選單。
- 章節以關卡卡片形式呈現。
- 筆記區維持整齊、清楚的閱讀排版。
- 測驗區使用 RPG 戰鬥介面。
- 怪獸採用簡單、可愛的像素造型。
- 使用像素感邊框、按鈕、血量條及星級圖示。
- 專業筆記內文使用容易閱讀的繁體中文字型。
- 像素風格主要使用於標題、裝飾與遊戲介面。
- 避免讓所有中文內文使用難以閱讀的像素字體。

### Colors

建議色彩：

- 背景：米白或柔和淺色。
- 主色：深藍紫色。
- 輔色：薰衣草紫、淡藍、薄荷綠。
- 血量：珊瑚紅。
- 星星：金黃色。

同一功能的顏色應保持一致。

### Responsive Design

- 支援桌面和手機版。
- 手機畫面不可出現水平溢出。
- 文字、按鈕與選項必須清楚易讀。
- 手機版優先使用單欄排版。
- 點擊區域必須足夠大。

### Animation

V1.0 僅實作：

1. 答對時怪獸短暫晃動或閃爍。
2. 怪獸血量變化。
3. 勝利時的簡單怪獸倒下或消失動畫。
4. 失敗時的簡單提示效果。
5. 結算時的星星顯示效果。

使用 CSS Animation 或簡單 JavaScript。

不使用大型遊戲引擎。應尊重使用者的 reduced-motion 系統偏好，動畫不可阻礙正常操作。

## 6. Page Structure

### 6.1 Home Page

首頁包含：

- NeuroQuest 網站名稱。
- 簡短的網站介紹。
- 冒險地圖或章節選擇區。
- 各章節名稱與開放狀態。
- 已開放章節的最佳星級。

每章以卡片或地圖節點呈現。

### 6.2 Available Chapters

V1.0 只有一章正式開放。

預設第一個章節為：

**突觸與神經傳遞（Synapses）**

正式章節內容須以使用者提供的資料為準。

其他章節可以預留入口，但必須：

- 明確顯示 Coming Soon。
- 不允許進入空白內容頁。
- 不顯示虛假的星級與完成紀錄。
- 未來可改為正式開放。

### 6.3 Note Page

採用單頁式閱讀設計。

內容應包含：

1. 章節名稱（中英文）。
2. 學習目標。
3. 重要概念與定義。
4. 主要機制與流程。
5. 易混淆概念比較。
6. 圖表或簡單示意圖。
7. 章節重點整理。
8. 開始怪獸挑戰按鈕。

較長的內容可以使用可展開的區塊。

使用者可以自由展開、收合與重新閱讀，不需完成閱讀才能進入測驗。

筆記不得只保留過度精簡的摘要而遺漏重要課程內容。

## 7. Content Quality Rules

生理心理學內容具有專業性，正確性優先於視覺效果。

必須遵守：

- 優先使用使用者提供的課程筆記及教材。
- 不擅自捏造研究結果、神經機制或名詞定義。
- 專有名詞首次出現時盡量包含中英文。
- 使用易懂但科學上正確的說明。
- 必要時使用表格比較相似概念。
- 不確定的內容要標示待確認。
- 不得在來源不足時自行補入看似合理但未經確認的考試重點。
- 學習資料與題目應可以追溯到其來源或對應筆記段落。
- 題目與詳解需經人工檢查後才能視為正式內容。

教材未提供之前，可以先用明確標示的示範資料開發版型，但不得將示範內容當成已核對的正式課程教材。

## 8. Quiz Requirements

每個正式開放的章節包含 10 題。

### Question Types

- 4 題是非題（True / False）。
- 6 題四選一選擇題（Multiple Choice）。

### Cognitive Levels

- 5 題基礎概念與理解。
- 5 題情境應用與推理。

題型與認知層次為兩個獨立維度，必須同時滿足數量規定。

### Question Data

每題應包含：

- `id`：章節內唯一且穩定的題目 ID。
- `type`：true_false 或 multiple_choice。
- `level`：basic 或 application。
- `question`：題幹。
- `options`：選項陣列。
- `correctAnswer`：正確答案索引。
- `explanation`：答案詳解。
- `sourceRef`：對應教材或筆記段落識別值。

資料範例：

    {
      id: "syn-001",
      type: "true_false",
      level: "basic",
      question: "題目文字",
      options: ["正確", "錯誤"],
      correctAnswer: 0,
      explanation: "答案解析",
      sourceRef: "synapses-section-01"
    }

此範例僅說明資料結構，不代表正式題目。

### Randomization

- 每次開始挑戰時，將固定 10 題隨機排列。
- 同一輪挑戰不得出現重複題目。
- V1.0 不隨機排列題目選項。
- 每題使用固定 ID 對應答案與解析。
- 不得因隨機排列而發生答案錯位。

### Answer Submission

- 每題只能正式提交一次。
- 使用者選擇答案後，按下確認按鈕送出。
- 提交後鎖定答案。
- 立即顯示正確或錯誤。
- 顯示正確答案及詳解。
- 使用者點擊下一題後繼續。
- 不允許重複提交導致重複得分。
- 所有 10 題完成後進入結算。

## 9. Monster Battle System

### Basic Rules

- 每章對應一隻怪獸。
- 怪獸初始 HP 為 10。
- 玩家每答對一題，怪獸 HP 減少 1。
- 答錯時 HP 不變。
- HP 不得低於 0 或高於初始值。
- 目前 HP = 10 - 本輪答對題數。
- 一輪必須完成全部 10 題。

### Victory Rules

答對至少 6 題視為成功擊敗怪獸。

即使在第 6 題已達到勝利門檻，仍必須繼續完成剩餘題目，以決定最終星級。

正式勝利或失敗動畫在第 10 題作答完成後觸發。

### Star Ratings

| Correct Answers | Result | Stars |
|---|---|---|
| 0–5 | 失敗 | 0 |
| 6–7 | 勝利 | 1 |
| 8–9 | 優秀勝利 | 2 |
| 10 | 完美勝利 | 3 |

星級判定必須由單一共用函式負責，不得在不同頁面重複撰寫不一致的判定規則。

## 10. Results and Review

完成 10 題後，顯示：

- 怪獸勝利或失敗畫面。
- 本次正確題數。
- 本次星級。
- 該章歷史最佳星級。
- 錯題清單。
- 每題錯誤答案、正確答案與詳解。
- 重新挑戰按鈕。
- 返回筆記或首頁按鈕。

失敗時應鼓勵使用者複習錯題，不要使用羞辱或責備性的文字。

即使本次完全答對，也應顯示明確的完成結果。

## 11. Progress Saving

使用 browser localStorage 儲存各章最佳星級。

規則：

1. 每個章節使用獨立的 chapterId。
2. 最佳星級只可以維持或提高。
3. 新成績低於舊成績時，不得覆蓋舊紀錄。
4. 0 星代表已挑戰但未獲勝。
5. 尚未挑戰與已挑戰但 0 星應可區分。
6. 儲存資料使用具版本識別的 key。
7. localStorage 無法使用時，遊戲仍須正常運作。
8. 不儲存姓名、帳號或其他個人資料。
9. 不提供跨瀏覽器或跨裝置同步。

V1.0 不需儲存進行到一半的挑戰。

頁面重新整理後，可重新開始當前挑戰，但之前的最佳星級應保留。

## 12. Accessibility and UX

- 所有互動選項應使用語意正確的 HTML 控制元件。
- 按鈕與選項可透過鍵盤操作。
- 必須提供清楚的焦點樣式。
- 正確與錯誤不能只靠顏色區分。
- 主要文字與背景應有足夠對比。
- 動畫不得是唯一的回饋方式。
- 長篇筆記應提供清楚的段落標題。
- 不應出現無法返回的畫面。
- 載入或資料錯誤時，提供友善且可理解的提示。

## 13. Reusable Architecture

專案必須具有可擴充性。

每個章節的資料應至少包含：

- chapterId
- title
- englishTitle
- status
- noteData
- quizData
- monsterConfig

新增章節時：

1. 建立新章節資料。
2. 加入章節清單。
3. 沿用既有筆記版型。
4. 沿用既有測驗與戰鬥邏輯。
5. 更換對應怪獸設定。
6. 確認章節狀態。
7. 測試新章節與原有章節。

不得為每個新章節複製一套獨立計分程式。

## 14. Development Workflow

每次接到新的開發要求時：

1. 先檢查 CLAUDE.md 與現有專案。
2. 確認需求是否已由既有功能支援。
3. 簡短說明預計建立或修改的檔案。
4. 優先重用現有架構。
5. 完成修改。
6. 執行可用的測試。
7. 回報修改內容與測試結果。

若任務過大，應拆成可驗收的小階段。

不要在未經使用者同意時：

- 擅自增加大型功能。
- 更換整個技術架構。
- 刪除已核對的教材內容。
- 修改星級與勝負規則。
- 覆寫使用者提供的原始教材。
- 安裝不必要的外部依賴。

涉及刪除檔案、修改大量既有內容或公開發布時，必須先說明影響並取得確認。

## 15. Testing Requirements

至少測試：

### Quiz Validation

- 每章恰好有 10 題。
- 包含 4 題是非與 6 題四選一。
- 包含 5 題基礎及 5 題應用題。
- 每題 ID 唯一。
- 每題只有一個有效正解。
- 每題都有非空白詳解。
- 每題有可供核對的來源欄位。
- 隨機題序不會造成題目重複或答案錯位。

### Score Validation

測試答對 0 到 10 題的全部情況。

必須確認：

- 答對 5 題為 0 星。
- 答對 6 題為 1 星。
- 答對 7 題為 1 星。
- 答對 8 題為 2 星。
- 答對 9 題為 2 星。
- 答對 10 題為 3 星。

### Interaction Validation

- 一題不能重複得分。
- 提交後無法更改答案。
- 怪獸血量正確。
- 題目可以正常切換。
- 錯題回顧正確。
- 重新挑戰可以正常重置。
- 最佳星級不會被較低成績覆蓋。
- Coming Soon 章節不可誤入。
- 手機版可正常操作。

### Deployment Validation

- 首頁可從 GitHub Pages 開啟。
- 所有 JS、CSS、圖片及資料可正常載入。
- 沒有因為子路徑造成資源載入失敗。
- 瀏覽器沒有阻礙功能的 JavaScript 錯誤。
- 手機與桌面版的主要功能正常。

不得在未執行測試時聲稱所有測試通過。

若測試工具不可用，須說明未驗證項目。

## 16. Development Priority

開發順序：

**Phase 1 — Foundation**
- 建立專案結構。
- 完成首頁及章節選單。
- 建立章節資料格式。

**Phase 2 — Learning**
- 完成第一章筆記。
- 建立可展開內容區塊。
- 加入開始挑戰入口。

**Phase 3 — Quiz**
- 建立題庫。
- 完成隨機題序。
- 完成答題、批改與詳解。

**Phase 4 — Battle**
- 加入怪獸。
- 加入血量與星級。
- 完成結果頁及錯題回顧。

**Phase 5 — Polish**
- 加入基本像素動畫。
- 支援手機排版。
- 測試及修正問題。

**Phase 6 — Release**
- 更新 README.md。
- 驗證新增章節的可擴充性。
- 部署至 GitHub Pages。

若時間不足，優先保證 Phase 1–4 的功能完整與正確，並完成可公開瀏覽的部署。

視覺特效可以簡化，但不可犧牲核心學習功能。

## 17. Completion Criteria

V1.0 必須達成：

- 可公開瀏覽的網站。
- 正常顯示的首頁。
- 一個完整的課程章節。
- 一套 10 題測驗。
- 正確的戰鬥及計分機制。
- 正確的星級判定。
- 可正常使用的錯題回顧。
- 基本的像素 RPG 風格。
- 可持續擴充的章節資料架構。
- 已建立且維護 CLAUDE.md。
- 已建立 README.md。
- 已完成基本功能測試。
- 已提供 GitHub Repository 及 GitHub Pages 網址。

完成後，請以繁體中文報告：

1. 完成的功能。
2. 建立或修改的主要檔案。
3. 執行過的測試與結果。
4. 尚未完成或需要人工確認的部分。
5. 如何在未來新增新章節。

---

## Final Principle

NeuroQuest 的核心不是開發一款大型 RPG，而是建立一個能持續成長、兼具學習效果與遊戲趣味的生理心理學平台。

**Content correctness first. Reusable architecture second. Game aesthetics third.**

當需求彼此衝突時，依照此優先順序處理，並向使用者說明取捨。
